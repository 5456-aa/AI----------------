## 关于「来源覆盖」这个短板（诚实说明）

本系统接入 **11 个可用来源**（附件2 内 9 个 + 清单外 2 个），但不同来源对不同方向的产出差异极大：

| 来源类型 | 代表 | 机会率 | 说明 |
|---|---|---|---|
| 问答社区 | SegmentFault | 54.3% | 最强，天然是「提问」形态 |
| 技术问答 | Stack Overflow | 50.0% | 技术向，但量少 |
| 开发者社区 | GitHub | 20.7% | 技术向主力 |
| 视频社区 | 哔哩哔哩 | 3.5% | 补 C 端覆盖，机会稀 |
| 技术教程 | 掘金 / 博客园 / 开源中国 | 0~3% | 几乎无需求信号 |
| 资讯媒体 | 量子位 / IT之家 / InfoQ | 0% | 仅作背景 |

**结论**：
1. **机会密度由来源性质决定，不由方向决定**——同为技术社区，问答形态天然产生需求，教程形态天然不产生；
2. 医疗、法律批次只有 2~3 个源出数，是**来源配置问题**而非系统能力问题：默认来源缺少该领域垂直社区；
3. 改进路径已内置：在「发起新需求」界面勾选更多来源、或手填更精确检索词，无需改代码；
4. 弃用来源均有据：V2EX 网络不可达；36氪/机器之心 无公开 RSS；**CSDN robots.txt 为 `Disallow: /`**；Kaggle 需登录态；Product Hunt 需 OAuth。
5. 哔哩哔哩需要设备标识（buvid3）才能调用搜索接口，已在采集器中内置并做 412 重试；仅取标题与简介，不取弹幕与评论。
